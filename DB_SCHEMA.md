## 1. Schema source of truth = Go structs

There is **no SQL schema definition** in this repo. Tables are generated by GORM v2 (`gorm.io/gorm v1.31.x`, see `go.mod`) from the structs in `internal/models/`.

| File | Model | Table (GORM inflection) |
| --- | --- | --- |
| `internal/models/user.go` | `User` | `users` |
| `internal/models/game.go` | `Game` | `games` |
| `internal/models/language.go` | `Language` | `languages` |
| `internal/models/pack.go` | `Pack` | `packs` |
| `internal/models/rarity.go` | `Rarity` | `rarities` |
| `internal/models/storage.go` | `Storage` | `storages` |
| `internal/models/media.go` | `Media` | `media` |
| `internal/models/card.go` | `Card` | `cards` |

Facts:

- No `Table()` name override exists anywhere → table names come from GORM's default inflector. Confirm live with `psql -c '\d cards'` rather than trusting the inflection (notably `media`).
- `migrations/` directory is **empty**. `sample-data/initialize.sql` is a seed fixture, not a schema definition.
- Connection: `internal/database/connection.go:11 NewConnection(databaseURL, databaseDriver)` → `gorm.Open(dialector, &gorm.Config{})` + `sqlDB.Ping()`. `Close(db)` at `connection.go:43`.
- Dialectors available: `gorm.io/driver/{postgres,mysql,sqlite}`.

### Foreign-key wiring (declared explicitly)

`pack.go:18` `Game` → `packs.game_id`; `pack.go:20` `Language` → `packs.language_id`.

`card.go` (each FK field is a plain `uint` + an association struct sharing the same `column:`):

| Line | Field pair | FK column on `cards` | Nullable? |
| --- | --- | --- | --- |
| 26/27 | `GameID` / `Game` | `game_id` | `not null` |
| 28/29 | `LanguageID` / `Language` | `language_id` | `not null` |
| 30/31 | `PackID` / `Pack` | `pack_id` | `not null` |
| 32/33 | `RarityID` / `Rarity` | `rarity_id` | `not null`, `default:1` |
| 34/35 | `StorageID` / `Storage` | `storage_id` | **nullable** (no `not null`) |
| 36/37 | `MediaID *uint` / `Media *Media` | `media_id` | **nullable** |

Note the FK column for media is **`media_id`, not `provider_id`** — `gorm:"column:media_id;foreignKey:MediaID;constraint:OnUpdate:CASCADE,OnDelete:SET NULL;"`. `Media.Provider` (`media.go:14`) is an unrelated plain `string` column on the `media` table.

### Soft delete

Only `User` (`user.go:18`) and `Card` (`card.go:24`) have `DeletedAt gorm.DeletedAt`. `Game`, `Language`, `Pack`, `Rarity`, `Storage`, `Media` have only `CreatedAt`/`UpdatedAt` → **hard delete**.

### FK constraints in the DB

`connection.go` passes a bare `&gorm.Config{}`; it does **not** set `DisableForeignKeyConstraintWhenMigrating: true`. With GORM v2 that means `AutoMigrate` emits real `fk_*` foreign-key constraints for the associations above. Consequence: deleting/replacing referenced rows is constrained, and dropping a FK later requires `ALTER TABLE ... DROP CONSTRAINT fk_...`.

## 2. How you update the schema (the live path)

1. Edit the struct in `internal/models/<name>.go`. That is the entire change — there is no second file to touch.
2. `cmd/api/main.go` calls `database.RunMigrations(...)` on **every** process start.
3. `internal/database/migrations.go:14 RunMigrations` → `_ = migrationsPath` (line 15: `MIGRATIONS_PATH` is accepted and **discarded**) → opens its own connection via `NewConnection` → `AutoMigrate(db)` (line 22).
4. `migrations.go:42 AutoMigrate` builds `modelsToMigrate` (line 43) and calls `db.AutoMigrate(modelsToMigrate...)` (line 54), then `CreateDefaultSeedData(db)` (line 58) in the same flow.

Order in `modelsToMigrate` is dependency-first:

```go
User, Game, Language, Pack, Rarity, Storage, Media, Card
```

A new model that carries FKs must be appended **after** its dependency models, otherwise AutoMigrate can fail on a missing target table.

`make migrate-up` (Makefile:55) is an `@echo` stub — it runs nothing. The only real entry points are `cmd/api` (auto, on boot) and `cmd/migrate up`.

## 3. What AutoMigrate will and will not do

Per GORM docs (`gorm.io/docs/migration.html`, fetched 2026-07-09):

**Will do**

- create missing tables, columns, indexes, foreign-key constraints
- change an existing column's type and size
- add a `NOT NULL` constraint

**Will never do**

- remove unused columns, foreign tables, indexes, or FK constraints
- remove a `NOT NULL` constraint
- rename a column or table
- add CHECK constraints, partial-unique constraints, `ON UPDATE` auto-increment

Docs state AutoMigrate is "only designed for development and simple schema updates" and that complex changes need third-party tools.

Postgres-specific: `ALTER TABLE ... ADD/DROP COLUMN` is not atomic, so a failing AutoMigrate can leave the DB in an intermediate state — and it re-runs on the next boot.

Traps specific to this schema:

- Adding a `not null` field with **no** `default:` to a non-empty table fails in Postgres. Example shape: `Media.Provider` (`media.go:14`, `not null`, no default).
- `uniqueIndex` on `users.email` (`user.go:12`) fails if existing rows collide.
- `size:` changes on an existing column widen/shrink in place; shrinking can fail on existing data.

## 4. Rollback: not available

| Path | Behaviour |
| --- | --- |
| `migrations.go:25 RollbackMigrations` | `return fmt.Errorf("rollback is not supported when using GORM auto-migration")` — always errors |
| `migrations.go:34 GetMigrationVersion` | always `(0, false, nil)`; `cmd/migrate version` prints a meaningless `Current version: 0` |
| Makefile `migrate-down` (59), `migrate-rollback` (62), `migrate-create` (65), `migrate-version` (68), `migrate-force` (71) | `@echo` stubs, invoke no code |
| `cmd/migrate/main.go down` | calls `RollbackMigrations` → always errors |
| `cmd/migrate/main.go create` | writes `migrations/<ts>_<name>.{up,down}.sql` that **nothing reads** |
| `cmd/migrate/main.go force` | the only real golang-migrate call, but `migrations/` is empty; its sqlite branch is broken (`sql.Open("sqlite", …)` — no such `database/sql` driver registered; golang-migrate expects `sqlite3`) |

Conclusion: **no version tracking, no history, no undo.** Schema drift is one-way.

## 5. How to reverse a change in practice

1. **Manual SQL** (the normal path). `docker exec -it cardtalogue_psql_container bash` → `psql` → write the inverse yourself:
   - `ALTER TABLE cards DROP COLUMN foo;`
   - `ALTER TABLE cards DROP CONSTRAINT fk_...;` for FKs
   - inspect first with `\d cards`
2. **Destructive reset** (dev only): `make delete-db` (podman, Makefile:105) / `make delete-db-docker` (109) → `docker volume rm -f cardtalogue-backend_postgres_data`, then `make db-up` (113); the app re-seeds defaults on next boot. Named volume is `postgres_data` in `docker-compose.yml`. For sqlite (`file:./data.db`) delete the file by hand — `make clean` (49) only removes `bin/` and `coverage.out`.
3. **Introduce real migrations** if you want rollback in production: add SQL to `migrations/`, rewire `cmd/migrate` `up`/`down` to golang-migrate, **and** remove `RunMigrations` from `cmd/api/main.go` — otherwise AutoMigrate and the SQL files fight each other.

## 6. Repo traps on day one

- `.env` sets `DATABASE_URL=postgres://user:password@172.17.0.1:5432/dbname?sslmode=disable` but defines **no `DATABASE_DRIVER`** → `config.go:47` defaults to `sqlite`, so the sqlite dialect receives a `postgres://` string. Set `DATABASE_DRIVER=postgres`.
- Makefile defaults: `DATABASE_DRIVER ?= sqlite` (2), `DATABASE_URL ?= file:./data.db` (3); `run` (36) exports those three vars, so use `make run DATABASE_DRIVER=postgres DATABASE_URL=...`.
- `RunMigrations` opens a **second** `gorm.DB` and never closes it; only `cmd/api`'s handle is closed.
- `make fill-sample` (103) is broken: `psql … -d dbname -a -f …` — `-a` is not a psql flag and `-d dbname` is a literal database name.
- README "Database Schema" and "Run Migrations" sections are stale: they document Users + Items and claim `make migrate-up` runs migrations.

## Recommendation for a new maintainer

Keep AutoMigrate for local dev, but treat it as **additive-only**: never rename or delete a field/column. Do removals, renames, and constraint changes by hand-written SQL. Replace the AutoMigrate shim with real golang-migrate files only when you actually need production-grade, reversible schema control.
